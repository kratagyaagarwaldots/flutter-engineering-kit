Six ways an AI-built app goes wrong.

Each group of skills exists because of one of these. None of them is about writing code faster.

Workflow

One loop, from idea to store.

Each step's output is the next step's input. Use the whole loop, or only the steps you need: nothing here owns your process.

Any starting point

New app, your app, or someone else's.

Setup records what the repo already uses, so every generator writes in that style. A Riverpod app gets Riverpod; a GetX app gets GetX.

From scratch greenfield

The full loop, with the kit's defaults scaffolded into lib/core.

  1. Settle requirements and the design language
  2. Screens first, on fixture data
  3. Upgrade to the real API when it lands

Your existing app brownfield

Setup learns your stack; you start at the change.

  1. Explain the area you are touching
  2. Sketch the change, then build test-first
  3. Review and prove before committing

An inherited app takeover

Code you didn't write and don't trust yet.

  1. Audit: build health, dependencies, security
  2. Fix the foundation before features
  3. Modernize only the screens you touch

Principles

What the kit imposes, and what it doesn't.

Your stack, not ours

No skill names a state-management library. The project's stack is recorded once in docs/agents/project.md and every skill reads it.

Proven, not claimed

Every change reports the verification rung it reached: static, unit, widget, golden, or a real device. "Not proven" is a valid answer; a wrong rung is not.

Small and composable

Each skill does one job and calls others by name. Read any of them in five minutes, fork the ones you want to change.

Rules that enforce themselves

Formatting, fixture markers and secret scanning run as hooks. A rule that fails a build beats a rule that has to be remembered.
